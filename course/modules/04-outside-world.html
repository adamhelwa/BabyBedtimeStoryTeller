The Outside World

Three calls to OpenAI — and the one that almost didn't work

Three trips out, every story

Every time someone taps "Tonight's Story," the browser makes three separate API calls, straight to OpenAI's servers:

POST /v1/chat/completions Write the story — called with the Writer's instructions
POST /v1/chat/completions Same address, second time — called with the Safety Reviewer's instructions instead
POST /v1/audio/speech Narrate the cleared text as an audio file

The doorman checking the guest list

Browsers are protective. Before letting a web page's code fetch data from someone else's server, the browser secretly asks that server first: "is this website actually invited to talk to you?" That question-and-answer is called CORS.

It's exactly like a doorman with a guest list at the entrance of a building. The server has to have written your name down in advance (sent back the right permission headers) — otherwise the doorman turns you away at the door, no matter how legitimate your reason for visiting.

🚪
Not every OpenAI door has a guest list

chat/completions and audio/speech both have this app's requests "on the list" — OpenAI's server sends back the right permission headers, so the doorman waves the browser through. /v1/moderations — OpenAI's dedicated safety-check endpoint — sends back no such headers at all. Not "denied." Just silence. And silence means the doorman never lets you in.

What actually happened

The original plan was to use OpenAI's purpose-built /v1/moderations endpoint for the safety check — it's the tool literally designed for this job. It never got a chance to run. Key Insight

A blocked-by-CORS request and a genuinely dead internet connection look identical to your code — both just throw a generic error with no useful detail. The only way to tell them apart is to open the browser's own error console, which most users never see. That's what made this bug tricky: the app's own error message ("couldn't reach OpenAI") was confidently wrong.
