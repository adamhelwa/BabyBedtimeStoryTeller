What This App Does

One click, and the app switches scenes

Under the hood, those four screens are just three HTML sections that get shown or hidden. One small function controls all of it.

CODE 
function showScreen(id) {
    [els.setupScreen, els.loadingScreen, els.storyScreen].forEach(function (s) {
      s.classList.toggle("active", s.id === id);
    });
}
PLAIN ENGLISH

Define a reusable job: "show this one screen, hide the rest."

Look at all three screens — setup, loading, and story — one by one...

...and turn the "active" (visible) label on for the one whose ID matches, off for the other two.

End of the check.

That's the whole scene-switcher. Three screens, one rule.

The surprising part: there's no server

Most apps you've used have a company's server sitting in the middle — your phone talks to it, and it talks to everything else. This app skips that step entirely.

⚡
No Middleman

Think of it like a phone with no operator. Old phones routed every call through a switchboard person. This app dials straight out — your browser calls OpenAI directly, with no company computer answering in between.

That single design choice is the thread running through this whole course. It's why the API key lives in your browser instead of on a server, why three separate requests go out per story, and — in Module 4 — why one of those requests almost didn't work at all.

Meet the Actors

One performer, three costumes — and a browser that remembers

A very small cast

Most apps have a big cast: a frontend, a backend, a database, maybe a queue. This app has almost none of that. Here's the whole cast list:

🖥️
The Browser (the whole app)

Shows the screens, remembers your API key, plays the audio — everything the user sees.

🤖
OpenAI

The only outside service this app ever talks to. It plays three different roles — more on that below.

📖
The Fallback Library

Two pre-written stories, baked right into the code, ready in case something goes wrong.

One actor, three roles

A small theater company will often have one performer play three different characters in the same show — different costume, different voice, same person underneath. That's exactly what OpenAI does in this app.

✍️

The Writer

Given a name and a theme, writes a short, calming story.

🛡️

The Safety Reviewer

Reads the story back and decides: is this actually okay for a 2-to-5-year-old?

🎙️

The Narrator

Takes the cleared text and reads it aloud in a calm voice.

💡
Key Insight

All three roles are the same underlying AI model, just given a different job in each request. The Writer and the Safety Reviewer are quite literally the exact same endpoint called twice, with different instructions each time. You'll see exactly why in Module 4.

Where things are remembered

With no server, there's no database anywhere. The only thing this app remembers between visits is one item, kept in the browser itself:

CODE 
function getKey() { return localStorage.getItem(STORAGE_KEY) || ""; }
function setKey(k) { localStorage.setItem(STORAGE_KEY, k); }
PLAIN ENGLISH

To read the saved key: ask the browser's own storage for it, or hand back an empty string if there isn't one yet.

To save a key: write it into that same storage box.

localStorage is a little storage locker that belongs to your browser, not to any company. That's the whole "database" this app has — and it's the only thing that survives if you close the tab and come back tomorrow.

03

How the Pieces Talk

Texting, not voicemail: why each step waits for the last one to answer

Waiting for the reply bubble

When you text someone, you usually watch for the "..." typing bubble before you send your next message — you don't fire off five texts in a row hoping they land in order. Code can work the same way.

In JavaScript, this waiting is called async code, and the word that means "wait right here for the reply" is await.

Watch the conversation happen

Here's the actual back-and-forth between the browser and OpenAI for one story, message by message:

🖥️
Browser

Write a calm story for Maya, about a shy dragon.

🤖
OpenAI (Writer)

Here's the title and story, as JSON: {"title": "...", "story": "..."}

🖥️
Browser

Now review that same story — is it safe for a 2-to-5-year-old?

🤖
OpenAI (Safety Reviewer)

{"safe": true}

🖥️
Browser

Cleared. Please narrate this text out loud.

🤖
OpenAI (Narrator)

🔊 [audio file attached]

?

Notice the Browser never sends message 3 (narrate this) until message 2 (the safety check) has actually replied. That's await in action: each line pauses until the reply arrives.

The same conversation, as code

This is the real loop that runs that conversation. It tries up to twice to get a story that passes the safety check:

CODE 
while (attempt < 2 && !cleared) {
  attempt++;
  var result = await callChat(name, theme, key);
  title = result.title;
  story = result.story;
  cleared = await checkModeration(story, key);
}
PLAIN ENGLISH

Keep trying — but stop after 2 attempts, or as soon as a story passes.

Count this attempt.

Ask the Writer for a story, and wait right here until it replies.

Save the title it sent back...

...and the story text it sent back.

Ask the Safety Reviewer about that story, and wait for its verdict before looping again.

If it wasn't cleared, and there's an attempt left, go around again.

💡
Key Insight

Without await, this code would fire off the safety check before the story even finished being written — like reading a book's review before the author has typed the last page.

04

The Outside World

Three calls to OpenAI — and the one that almost didn't work

Three trips out, every story

Every time someone taps "Tonight's Story," the browser makes three separate API calls, straight to OpenAI's servers:

POST /v1/chat/completions Write the story — called with the Writer's instructions
POST /v1/chat/completions Same address, second time — called with the Safety Reviewer's instructions instead
POST /v1/audio/speech Narrate the cleared text as an audio file

The doorman checking the guest list

Browsers are protective. Before letting a web page's code fetch data from someone else's server, the browser secretly asks that server first: "is this website actually invited to talk to you?" That question-and-answer is called CORS.

It's exactly like a doorman with a guest list at the entrance of a building. The server has to have written your name down in advance (sent back the right permission headers) — otherwise the doorman turns you away at the door, no matter how legitimate your reason for visiting.

🚪
Not every OpenAI door has a guest list

chat/completions and audio/speech both have this app's requests "on the list" — OpenAI's server sends back the right permission headers, so the doorman waves the browser through. /v1/moderations — OpenAI's dedicated safety-check endpoint — sends back no such headers at all. Not "denied." Just silence. And silence means the doorman never lets you in.

What actually happened

The original plan was to use OpenAI's purpose-built /v1/moderations endpoint for the safety check — it's the tool literally designed for this job. It never got a chance to run. Every attempt failed at the doorman, before OpenAI's server even saw the request. Here's the fix, with the reasoning left in as a comment:

CODE 
// The dedicated /v1/moderations endpoint doesn't send CORS headers, so it can't be
// called from a browser at all. Chat completions does support CORS, so the safety
// gate runs there instead, as a second, independent LLM call acting as a judge.
async function checkModeration(text, key) {
  var res = await fetch("https://api.openai.com/v1/chat/completions", {
    ...
  });
PLAIN ENGLISH

A left-behind note explaining why this isn't the "obvious" endpoint...

...because that obvious endpoint silently fails every single time, from a browser.

...so this one uses the endpoint that's actually reachable instead.

Define the safety check as its own function.

And send it to chat/completions — the same door the Writer already used.

💡
Key Insight

A blocked-by-CORS request and a genuinely dead internet connection look identical to your code — both just throw a generic error with no useful detail. The only way to tell them apart is to open the browser's own error console, which most users never see. That's what made this bug tricky: the app's own error message ("couldn't reach OpenAI") was confidently wrong.

05

When Things Break

A spare tire, a printed photo, and a translator for bad news

Three plans for "what if"

Good code doesn't assume everything works. This app plans for three specific ways things can go wrong — and never lets any of them reach a parent as a scary error screen.

A spare tire in the trunk

What if the Safety Reviewer flags a story twice in a row, and the app runs out of retries? It doesn't show an error. It reaches for a backup — two pre-written, already-safe stories baked right into the code, like keeping a spare tire so a flat doesn't strand you on the road.

CODE 
var usedFallback = false;
if (!cleared) {
  var fb = FALLBACK_STORIES[Math.floor(Math.random() * FALLBACK_STORIES.length)];
  title = fb.title;
  story = fb.body;
  usedFallback = true;
}
PLAIN ENGLISH

Start by assuming the backup wasn't needed.

But if nothing ever passed the safety check...

...grab a random one of the two pre-written stories...

...and use its title and text instead of the AI's attempt...

...and remember that this was a backup, for later.

A printed photo, not a re-take

Tap "Replay" and the story plays again instantly — no loading spinner, no new request to OpenAI. That's because the audio isn't re-fetched each time; it's kept, like a printed photo you can look at again without asking the photographer to shoot it twice.

CODE 
var blob = await res.blob();
return URL.createObjectURL(blob);
PLAIN ENGLISH

Take the raw audio data OpenAI sent back...

...and turn it into a local link the browser can replay on its own, anytime, with no network involved.

That local link, called a blob URL, is what the Replay button actually uses:

CODE 
els.replayBtn.addEventListener("click", function () {
  els.audioPlayer.currentTime = 0;
  els.audioPlayer.play();
});
PLAIN ENGLISH

When Replay is tapped: rewind the same audio back to the start...

...and press play again. That's it — no fetching, no waiting.

A translator for bad news

When OpenAI does send back an actual error, the raw message is written for developers, not parents. One function's whole job is translating it:

CODE 
function friendlyErrorMessage(err) {
  if (err && err.status === 401) return "That API key was rejected...";
  if (err && err.status === 429) return "OpenAI is rate-limiting this key...";
  if (err instanceof TypeError) return "Couldn't reach OpenAI...";
  return (err && err.message) || "Something went wrong. Please try again.";
}
PLAIN ENGLISH

Given whatever went wrong...

...if it was "401" (a bad key), say so in plain words.

...if it was "429" (too many requests, too fast), explain that instead.

...if the network itself failed (which, as Module 4 showed, is also what a CORS block looks like), say that.

Otherwise, fall back to whatever message came with it, or a generic apology as a last resort.

💡
Key Insight

This pattern — catching a technical error and rewriting it for a human — is called an error status code lookup table. It shows up everywhere: the code checks a small number, and translates it into words a non-developer would actually understand.

A user reports seeing "Couldn't reach OpenAI — check your internet connection" right after generating five stories in quick succession. Based on friendlyErrorMessage, is that message actually accurate here?
